# 프로젝트 변경 이력 탐색 개선 설계

## 배경

프로젝트 상세페이지는 현재 판정 근거로 사용한 주의·장애 이벤트를 제외한 최근
변경을 최대 20건까지 한 번에 표시한다. DeployHub 프로젝트에는 18건이 그대로
노출되어 구성도, 판정 근거, 최종 배포 같은 현재 상태 정보보다 변경 이력이 더 큰
비중을 차지한다.

전역 `/events` 페이지와 `listTimelineEvents` 조회는 이미 존재한다. DB 조회는
프로젝트, 심각도, 변경 종류, 커서를 지원하지만 화면에서는 필터와 페이지 이동을
제공하지 않는다. 상세페이지는 최신 맥락만 보여 주고, 전체 탐색은 전용 페이지가
담당하도록 역할을 분리한다.

## 목표

- 프로젝트 상세페이지의 변경 이력을 최근 5건으로 줄인다.
- 추가 이력이 있으면 해당 프로젝트가 선택된 전역 변경 이력 페이지로 연결한다.
- 전역 변경 이력에서 프로젝트, 심각도, 변경 종류를 조합해 필터링한다.
- 필터와 페이지 위치를 URL로 표현해 새로고침, 공유, 뒤로 가기를 지원한다.
- 전역 이력에서 각 이벤트가 어느 프로젝트에 속하는지 알 수 있게 한다.
- 기존 Schema와 `listTimelineEvents`의 필터·커서 기능을 재사용한다.

## 비목표

- 변경 이벤트 Schema나 기록 방식을 바꾸지 않는다.
- 날짜 범위 선택, 자유 검색, 정렬 변경, CSV 내보내기는 추가하지 않는다.
- 프로젝트별 `/projects/[slug]/events` 페이지를 새로 만들지 않는다.
- 상세페이지에서 이력을 계속 펼치는 클라이언트 상태를 추가하지 않는다.
- 전체 건수를 계산하기 위한 별도 count 조회를 추가하지 않는다.

## 정보 구조

### 프로젝트 상세페이지

기존 `변경 이력` 카드는 `최근 변경` 카드로 바꾼다.

- 판정 근거 이벤트 ID를 제외하는 현재 동작은 유지한다.
- `listTimelineEvents`를 `limit: 5`로 호출한다.
- 카드에는 실제 반환된 이벤트 수를 `최근 N건`으로 표시한다.
- `nextCursor`가 있을 때만 `전체 변경 이력 보기` 링크를 표시한다.
- 링크는 실제 slug를 사용한 `/events?project=deployhub` 같은 형식으로 해당
  프로젝트 필터를 미리 선택한다.
- 이력이 없으면 현재의 빈 상태 문구를 유지한다.

상세페이지는 현재 상태를 이해하는 장소이므로 페이지네이션이나 필터를 넣지 않는다.

### 전역 변경 이력 페이지

기존 `/events` 페이지를 전체 이력 탐색 화면으로 확장한다.

- 필터는 `project`, `severity`, `kind` 세 가지다.
- 필터 폼은 GET 요청을 사용한다.
- 한 페이지는 최근 50건을 표시한다.
- 다음 페이지가 있으면 `다음` 링크를 표시한다.
- 다음 링크는 현재 세 필터와 `cursor`를 유지한다.
- 필터를 제출하면 폼에 `cursor`를 포함하지 않아 첫 페이지로 돌아간다.
- 프로젝트 필터를 사용하지 않은 전역 조회에서는 각 이벤트에 프로젝트 이름을
  표시한다.
- 프로젝트 필터가 적용된 상태에서는 행마다 같은 프로젝트 이름을 반복하지 않는다.

## 필터 계약

URL 검색 매개변수는 다음 값을 사용한다.

- `project`: 프로젝트 slug. 빈 값은 전체 프로젝트다.
- `severity`: `info`, `warning`, `critical` 중 하나다.
- `kind`: `health_status`, `container_status`, `container_health`, `deployment`,
  `ssl_expiry`, `sync_failure` 중 하나다.
- `cursor`: 다음 페이지의 불변 이벤트 sequence다.

화면에서는 enum 원문과 함께 이해 가능한 한국어 선택지 라벨을 제공한다. 선택하지
않은 필터는 URL에서 생략한다.

검색 매개변수는 서버에서 검증한다.

- 존재하지 않는 프로젝트 slug는 프로젝트 필터를 적용하지 않고 전체 조회로
  처리한다.
- 허용 목록에 없는 심각도와 변경 종류는 해당 필터를 무시한다.
- 양의 정수로 해석할 수 없는 커서는 무시하고 첫 페이지를 보여 준다.
- 잘못된 URL 값 때문에 페이지 전체가 오류 상태가 되지 않는다.

## 데이터 흐름

### 상세페이지

1. 프로젝트와 현재 판정 근거를 기존 방식으로 조회한다.
2. 판정 근거 이벤트 ID를 `excludeIds`로 전달한다.
3. 프로젝트 ID와 `limit: 5`로 타임라인을 조회한다.
4. 이벤트와 `nextCursor`를 렌더링한다.
5. 다음 커서가 있으면 프로젝트 slug를 포함한 전역 이력 링크를 만든다.

### 전역 이력 페이지

1. `searchParams`에서 필터와 커서를 읽는다.
2. 프로젝트 목록을 조회해 선택지를 만들고 slug를 ID로 해석한다.
3. enum 허용 목록으로 심각도와 변경 종류를 검증한다.
4. 유효한 값만 `listTimelineEvents`에 전달하고 `limit: 50`으로 조회한다.
5. 프로젝트 ID와 이름의 맵을 만들어 전역 결과의 행 라벨에 사용한다.
6. `nextCursor`가 있으면 현재 필터를 보존한 다음 링크를 만든다.

별도 DB 조회 API나 클라이언트 상태는 추가하지 않는다. 페이지와 필터는 계속 서버
렌더링한다.

## 컴포넌트 경계

- 프로젝트 상세 `page.tsx`는 조회 제한과 전체 이력 링크를 책임진다.
- 전역 `/events/page.tsx`는 검색 매개변수 검증, 프로젝트 선택지, 페이지 링크를
  책임진다.
- 필터의 파싱과 URL 생성을 작은 순수 유틸리티로 분리해 조합과 잘못된 값 처리를
  독립 테스트한다.
- `TimelineList`는 이벤트 행 렌더링을 유지하고, 선택적으로 프로젝트 이름 맵을
  받아 전역 조회일 때만 프로젝트 라벨을 표시한다.
- `listTimelineEvents`의 공개 옵션과 반환 타입은 변경하지 않는다.

## 접근성과 반응형 동작

- 세 필터 모두 연결된 `<label>`과 네이티브 `<select>`를 사용한다.
- 필터 적용과 초기화는 키보드로 동작하는 링크 또는 버튼으로 제공한다.
- 현재 선택값은 서버 렌더링 시 선택된 상태로 복원한다.
- 좁은 화면에서는 필터가 세로로 쌓이고, 넓은 화면에서는 한 줄로 배치한다.
- 다음 링크에는 현재 페이지 이후의 기록을 연다는 의미가 드러나는 문구를 사용한다.
- 프로젝트 이름은 이벤트의 보조 맥락으로 표시하며 기존 severity와 시간 정보의
  읽기 순서를 방해하지 않는다.

## 오류 처리

- 잘못된 검색 매개변수는 필터 단위로 무시하며 유효한 다른 필터는 유지한다.
- 프로젝트가 삭제되었거나 slug가 바뀐 링크도 전체 이력 화면으로 안전하게 열린다.
- 이벤트가 없으면 필터 상태를 유지한 채 기존 빈 상태를 표시한다.
- 다음 커서가 없으면 페이지 이동 링크를 렌더링하지 않는다.

## 테스트와 검증

- 상세페이지가 `limit: 5`를 전달하는지 확인한다.
- `nextCursor`가 있을 때만 프로젝트 slug가 포함된 전체 이력 링크를 렌더링하는지
  확인한다.
- 프로젝트, 심각도, 변경 종류 필터를 각각 적용하고 조합할 수 있는지 확인한다.
- 필터 제출 URL에 이전 커서가 포함되지 않는지 확인한다.
- 다음 페이지 URL이 유효한 필터와 커서를 보존하는지 확인한다.
- 잘못된 project, severity, kind, cursor가 안전하게 무시되는지 확인한다.
- 전역 결과에는 프로젝트 이름이 표시되고 프로젝트 범위 결과에는 중복 표시되지
  않는지 확인한다.
- 빈 결과와 마지막 페이지에서 이동 링크가 사라지는지 확인한다.
- 기존 타임라인 조회의 커서·제한·제외 ID 테스트를 유지한다.
- `pnpm typecheck`, `pnpm test`, `pnpm --filter web build`를 실행한다.
